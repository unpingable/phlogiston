# P0 installed acceptance boundary

This is a required future acceptance procedure, not an executed receipt or deployment authorization. `validate-bundle --profile p0` checks source templates. `host-preflight` checks installed units and principals. Neither checks the actual installed application configuration, effective proxy routing, secret custody or runtime behavior. Both can pass while installed configuration is wrong. Do not mark P0 installed qualification passed on those results alone. The historical six-service procedure cannot substitute for this four-service P0 check.

An independent acceptance owner must name the candidate host, exact source/archive digest, configuration digests, service invocation identities, reviewer, time, evidence references and disposition. The current candidate uses `/etc/atproto-community-p0`, but the effective unit paths and accepted candidate manifest decide what is actually installed; reconcile those exact paths rather than assuming the historical `/etc/atproto-community` layout. Keep this technical receipt with the existing release evidence and link its outcome from the canonical launch item. Do not publish secret bytes or credential-bearing command output.

## Actual bytes to reconcile

- `/etc/atproto-community-p0/community-web.env` and the separate protected `community-web-secret.env`: verify public origin exactly `https://phlogiston.app`, `COMMUNITY_PROFILE=p0`, selected community and moderator DIDs matching the ready campaign, `COMMUNITY_P0_HOSTED_PDS_ORIGIN=https://phlogiston.social` and `COMMUNITY_P0_ALLOW_BLUESKY=true`, matching observer/socket paths, exact two operator pause paths, and no `COMMUNITY_P0_TEST_PDS_ORIGIN`, loopback identity resolver seams or integration fault settings. Inspect only an allowlist of nonsecret fields; never print `COMMUNITY_SNAPSHOT_SECRET`. Record protected file digests and owner/mode separately.
- `/etc/atproto-community-p0/communityd.toml`: verify selected curator DID/PDS and sole moderator against the ready campaign, `p0_profile="root_only"`, `p0_hosted_pds_origin="https://phlogiston.social"`, `p0_allow_bluesky=true`, exact admission pause path, operation journal present, distinct daemon/web UIDs, no policy peer UID, no test PDS origin, no loopback public endpoints and no fault injection. The community writer still targets only the hosted curator PDS; the mixed flag permits external Bluesky author reads. Credential references name protected custody; they are not permission to read the referenced credential into evidence.
- `/etc/atproto-community-p0/communityd.env`: verify `COMMUNITYD_APP_PASSWORD` names an absolute, protected credential-file path rather than containing an inline password. Inspect the referenced file's owner/mode and exact actor-credential JSON shape through a privileged validation step without printing its bytes. The daemon's PDS session must return the configured community actor DID; a moderator browser OAuth grant is separate.
- `/etc/atproto-community-p0/communitywatch.toml`: verify matching community/moderator, `p0_hosted_pds_origin="https://phlogiston.social"` and `p0_allow_bluesky=true`, no `p0_bluesky_only` or isolated-test flag/test PDS origin, actual public DID directory/current Jetstream base, and loopback-only query serving. Verify observer process environment and installed dependencies contain no writer credentials or authority writer adapter.
- Publication custody: reconcile the ready campaign's actual `publicationEvidence.manifestPath`, `acceptancePath`, and `receiptPath` against the installed files, accepted manifest digest, eight exact record references/CIDs, and independently verified current DNS/PDS readback. Do not infer publication from an example path or the candidate renderer; these paths may be outside `/etc/atproto-community-p0` when their protected custody requires it.
- Both pause files at the exact paths named by the installed web and authority configuration (currently `/etc/atproto-community-p0/p0-site-state` and `/etc/atproto-community-p0/p0-admission-state`): inspect the opened regular objects, owner/mode and exact `paused\n` contents before startup acceptance. The service principals must not be able to change these objects or their parent directory. Missing, symbolic-link, malformed or group/other-writable controls must refuse new work.
- Effective systemd units and all drop-ins: record hashes and verify the four selected services actually use those exact installed files/runtime bytes. No second writer, notifier or policy process may be active or startable under this P0 profile; run the existing principal/unit preflight against the candidate host. A repository `.service` template is not evidence of the effective unit.
- Effective Caddy configuration: verify only the selected `phlogiston.app` route forwards to the candidate app; its origin and OAuth metadata agree. Do not reuse the historical `community.phlogiston.app` browser origin, alter `.social`, or enable a test provider publicly. Record validation and route readback with configuration digests, without TLS/private material.

## Required runtime correspondence

With explicitly enrolled test identity custody, demonstrate the installed app advertises the submission-only scope and canonical callback, then complete the already-required real Bluesky lifecycle using the actual observer. Show an unknown participating DID, duplicate/uncertain outcomes, private decline recovery, both pauses, authenticated removal while paused, and anonymous exact-version rendering. Inspect actual running process identities and provider hosting; do not infer them from environment templates.

Bind app intake and private authority decisions to the selected community and provider mode. Use fresh public state, never relabel Juche qualification state. Retain the private decision/intake backup and rehearse recovery; rebuilding the read-only observer alone does not recover these states. A prior admission attempt with an unknown external effect remains reserved until safe reconciliation; exact absence at one instant does not rule out a late provider commit. A pause does not cancel a request already dispatched.

Acceptance must distinguish source tests, configuration inspection, installed runtime qualification and owner activation approval. Missing actual-host evidence means installed P0 qualification remains pending. Do not activate writes or replace the public static site merely because this checklist exists.
